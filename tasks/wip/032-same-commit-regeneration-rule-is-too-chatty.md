# Regenerating the board in the same commit is too chatty for a multi-session repo — make it on-demand

## The ruling

Smiley, 2026-08-12, as the skill's owner:

> The rule — *"regenerate any projection of `tasks/` in the same commit"* is way too chatty. I'm the
> owner of the skill so let's fix the source, nix that rule. Having the functionality available on
> demand is important, and the README should be explicit about how to generate the task board and
> also explain it's deliberately generated by hand to reduce churn in multi-developer environments.

The generator stays. The **obligation to run it on every status move** goes.

## Where the rule came from, so this is a reversal and not a rediscovery

[[005-worktree-removal-trap-and-no-regeneration-step]] added it on 2026-08-06, defect #2, reported
by the first outside session to use the skill. Its argument was real and is not being called wrong:

> split commits mean every bisect between them lands on a tree where the tracker and its view
> disagree.

**What that argument did not price is concurrency.** It reasoned about one session moving one task.
The board is a single file that every lane change rewrites, so in a repo where parallel sessions are
the norm it becomes the most-contended file in the tree — and the conflict it produces is *pure
ceremony*, because the file is derived. Nobody has ever needed to hand-merge two views of the same
directory.

## The measurement that decided it

Taken from `everything-has-a-price`, an adopter running the skill with concurrent sessions as its
default operating mode. All [Verified] on 2026-08-12:

| | |
|---|---|
| `docs/task-board.md` changed in | **204 of 894 commits** over 30 days — **23%** |
| `generate-task-board.py --check` runtime | **0.23s** |
| The CI job carrying that check plus ~15 other generators | **10s** |
| A full docs-only PR pipeline | **31–42s** |

**So the cost was never compute.** It is the collision: one PR merges, every sibling PR touching the
board goes `DIRTY`, and each one pays a re-merge, a regenerate, a push, and a *fresh* CI run. A
conflicting PR never starts CI at all, so it reads as a hung runner rather than a conflict — the
failure is mis-attributed as often as not. On 2026-08-12 a single two-PR sequence paid that twice,
on a change with **zero production diff**.

Worth stating plainly because it inverts the intuition: making the rule cheaper to *run* would not
have helped. It was already free to run.

## What changes

1. **`skills/task-lifecycle/SKILL.md` — delete the "Regenerate any projection of `tasks/` in the
   same commit" section** from the Commit block, including its `git grep` discovery snippet and the
   *"not optional politeness where a project gates it in CI"* line.
2. **Replace it with a short pointer**, not silence — the skill should still say a projection may
   exist, that it is refreshed **on demand**, and why the same-commit obligation was deliberately
   removed. A reader who finds a board and no instruction to update it must not conclude the skill
   forgot.
3. **`README.md` is not optional collateral.** Line ~38 currently advertises the behaviour as a
   headline feature — *"refuses to close a task whose criteria didn't all come true, **regenerates
   the board in the same commit**"*. That sentence becomes false the moment the rule goes. The
   README needs:
   - the explicit generate command, given as the normal way to refresh the board;
   - a stated reason: **the board is generated by hand, deliberately, to reduce churn in
     multi-developer environments**, with the contention argument in a line or two;
   - the "What's in the box" / generator rows reworded to match.
4. **`tasks/README.md`** — the copy adopters put in their own repo. Same correction, since it is the
   file that actually reaches them.
5. **`evals/done-when-reconciliation/case.yaml` grades the behaviour being removed.** Rewrite the
   expectations to the on-demand rule; do not delete the case to make it pass. ⚠️ The two line
   numbers this section originally gave were wrong — see the correction note below for the lines
   that actually score.

## ⚠️ The consequence to decide, not to discover

**The generator is also the structural gate.** Per [[009-adopters-cannot-run-the-board-or-the-gate]]
and task 007, `generate-task-board.py` is what refuses to build from a task missing its H1 or its
`## Done when` — that enforcement is the centerpiece of the README's argument, and *the same-commit
rule is what made it fire continuously*. Take the rule away and:

- **Projects with a CI `--check` gate** are unaffected in substance — the gate still fails a stale
  board, just at PR time rather than at commit time. This is most of the value, retained.
- **Projects without one** lose continuous enforcement entirely. The H1 / `## Done when` contract
  reverts to firing only when someone remembers to run the board — which is exactly the "structure
  over vigilance" trade this repository argues against elsewhere.

So the README's on-demand instruction has to say something about CI — but **not** a blanket
"wire in `--check`". See the coupling below; that recommendation is only right for one of the two
camps.

⚠️ Do not quietly widen this into re-litigating the structural gate itself. If the second bullet
turns out to need its own answer, file it rather than folding it in.

## ⚠️ Adopters running the CI gate must change something, or every task-move PR goes red

Stated because the first draft of this task got it wrong, and wrong in the direction that costs.
A `--check` gate fails on a **stale** board. A task move makes the board stale. So the two halves
are coupled:

| Skill says regenerate | CI runs `--check` | Result |
|---|---|---|
| yes (today) | yes | Green. Chatty — the state being fixed. |
| **no (after this)** | **yes** | 🔴 **Every task-move PR fails**, and the fix is to hand-run the generator — the same work, now discovered as a red build instead of prompted. Strictly worse than either alternative. |
| no | no | Green. Board drifts until someone refreshes it — the intended end state. |
| yes | no | Chatty, no guarantee. |

**So the guidance splits.** `--check` in CI is right for a project that wants the freshness
guarantee and will accept regenerating as part of a task move; a project optimising for low churn
— the case that motivated this task — should not run it on every PR. Offer the trade, name which
side each choice lands on, and let the adopter pick. `everything-has-a-price` is in the second camp
and will need to drop or relax its gate-7 row; that is the change that actually delivers the
benefit there.
